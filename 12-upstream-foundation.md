# 12 — Upstream Foundation

Parts 22–24. This document does for the upstream stages (Discovery, Planning, Specification, Coding) what `08-foundation.md` does for the downstream stages: problem statement, research foundation, and architecture integration. It assumes 08–11 have been read; it does not restate them.

## Part 22 — Upstream problem statement

### 22.1 What the upstream stages do

Four contiguous generative stages that produce the artifacts the downstream stages judge:

```
Discovery  → product brief + hypothesis ledger        (what problem, for whom, how we'd know)
Planning   → task DAG + worktree lanes + budget       (in what order, by whom, at what cost)
Spec       → EARS acceptance criteria + contracts +   (what "correct" means, machine-checkably)
             module-spec deltas + test skeletons
Coding     → diffs on worktree lanes, task by task,   (the change itself, ready for Code Review)
             opened as PRs into the §09 pipeline
```

Each artifact is generated by a **single writer**, checked by **deterministic tools first**, critiqued by a **parallel heterogeneous voter panel**, with every candidate finding **independently verified**, synthesized by a **Leader**, and released through a **gate** — the same machinery as §09, pointed at documents and plans instead of diffs.

### 22.2 Why the upstream stages exist

The downstream edition's own research base demands it. [MAST (arXiv:2503.13657)](https://arxiv.org/abs/2503.13657) attributes ~42% of multi-agent failures to specification and system-design flaws (the remainder: ~37% inter-agent misalignment, ~21% weak verification/termination) — failures that are *created* upstream and merely *detected* downstream, expensively. A Code Review stage that catches a bug caused by an ambiguous acceptance criterion has spent voter dollars on a defect a $0.02 `ears_lint` call would have prevented. The cheapest place to catch a defect class is the stage where it is born:

| Defect class | Born in | Caught today by | Cost ratio (prevention : detection) |
|---|---|---|---|
| Untestable / ambiguous requirement | Spec | Human confusion mid-coding, or never | ~1 : 50 (one lint call vs. a rework cycle) |
| Hidden task coupling | Plan | Merge conflict or Repo Graph voter | ~1 : 20 |
| Two writers, one file | Plan (lanes) | Corrupted worktree, lost work | ~1 : 100 |
| Unvalidated assumption shipped as fact | Discovery | Production metrics, weeks later | unbounded |
| Spec drift during implementation | Coding | Review confusion, "the spec is wrong anyway" culture | ~1 : 30 |

### 22.3 Engineering philosophy — the seven principles, applied to generation

The seven principles of §08.1.3 carry over unchanged. Their upstream consequences are non-obvious enough to state:

**P1 Deterministic control flow.** Which task the implementer picks next, whether a plan's DAG has a cycle, whether coverage is 100% — all code. LLMs draft and critique; Python routes.

**P2 Hooks enforce, skills guide.** `ears_lint` failing is a blocked gate, not a suggestion. The implementer's inability to write to test files (outside test-authoring tasks) is a filesystem-level hook, not a prompt instruction.

**P3 Vote, don't debate.** Critique voters never see each other's findings. There is no "workshop the brief together" mode — [Debate-or-Vote (NeurIPS 2025, arXiv:2508.17536)](https://arxiv.org/abs/2508.17536) applies to opinions about documents exactly as it does to opinions about diffs.

**P4 Heterogeneous models.** The Ambiguity voter and the SpecWriter must not share a model family — a model reviewing its own family's prose exhibits the same "looks fine to me" bias as same-family code review (§08.2.2.3).

**P5 The system compounds.** Upstream leaders emit STAR-L signals; recurring downstream findings whose root cause is upstream (an ambiguity class, a chronically underestimated task type) land as constraint updates to the *upstream* skills and templates via the same weekly human-reviewed PR loop (§09.8.4).

**P6 Structured documents, not dialogue.** The brief, plan, spec bundle, and SCR are typed YAML/markdown artifacts with schemas. Revision cycles pass `(artifact, structured fix list)` to a fresh-context writer — never a chat transcript. This is also the mitigation for multi-turn degradation: [LLMs get lost in multi-turn conversation (arXiv:2505.06120)](https://arxiv.org/abs/2505.06120) measures ~39% average performance drop across turns; the revision protocol makes every revision turn one.

**P7 Spec first-class; harness enforces; MCP transports.** Upstream agents get the same frontmatter contracts, fixture gates (8 fixtures, 87.5%), and MCP server allowlists. Three new servers appear (§13.31); none exceeds risk L1.

### 22.4 The one deliberate asymmetry: Coding is not a voting stage

§08.2.2.9's finding — multi-agent wins on parallel read-heavy tasks and loses on sequential write-heavy ones — is load-bearing here. Discovery/Plan/Spec critique is read-heavy: parallel voters are correct. **Code generation is write-heavy: it gets a single writer per worktree lane, a deterministic harness loop, and *no* voter panel of its own.** The voter panel that judges code already exists — it is the §09 Code Review stage. Duplicating it inside Coding would double cost for correlated findings. Coding's job is to make the PR *worth reviewing*: tests first, hooks green, evidence drafted, scope respected. Full rationale in ADR-U01 (§13.36).

### 22.5 Completion criteria (upstream system)

The upstream track is complete when all of the following hold:

1. `autoproduct spec <feature-brief>` produces an EARS spec bundle that passes `ears_lint` and coverage-matrix 100% on a real feature.
2. `autoproduct implement <task-id>` runs the coding loop end-to-end: context assembly → red test → green implementation → build gate → PR opened into the §09 pipeline.
3. All four upstream gates (U1–U4) are operational with HITL interrupts tested.
4. Every registered upstream voter has its 8 fixtures merged at ≥87.5% pass.
5. An SCR raised by the implementer round-trips: coding → spec revision → human approval → coding resumes, with the full trail in the YAML mirror.
6. The hypothesis ledger of one shipped feature has been reconciled against production telemetry by the Maintenance stage.
7. The five upstream metrics (§13.33.1) are computed for two consecutive weeks.
8. One feature has traversed all eight stages — idea to production — with every gate crossing logged.

### 22.6 The three merged cycles

The eight stages are the confluence of three management cycles, not a purely engineering pipeline (methodology reference, three-cycle model): the **Product cycle** (what to build, for whom, how success is known) owns Discovery and reappears as hypothesis reconciliation in Maintenance; the **Project cycle** (who, in what order, at what cost) owns Planning and the lane/budget machinery; the **SDLC** (how to build it correctly) owns Spec through Deployment. The stages are the single execution spine; the cycles are the three lenses every gate checks — which is why Gate U1's decisions are product decisions, U2's are project decisions, and U3/U4's are engineering decisions, all human where judgment is the point.

### 22.7 Uniform autonomy contract, extended

The §08.1.8 contract extends to eight stages. Upstream additions to the 3-fail-then-escalate table:

- **Discovery** — 3 REQUEST_CHANGES cycles on the same brief → ESCALATE_ARTIFACT_STUCK
- **Planning** — 3 dag/lane-check failures after revision → ESCALATE_ARTIFACT_STUCK; budget > cap → ESCALATE_BUDGET_EXCEEDED
- **Spec** — 3 cycles, or any core AC judged untestable after revision → ESCALATE_UNTESTABLE_CORE
- **Coding** — 3 failed attempts on one task → ESCALATE_TASK_FAILED; 3 SCRs on one task → ESCALATE_SPEC_UNSTABLE

Trust tiers (§09.11.5 framework) apply per stage; the upstream `forbidden_autonomous` additions are in §13.32.2. Headline: **problem selection, scope-tier lock, scope unlock, contract-breaking spec changes, and architecture acceptance are Assistive forever.**

## Part 23 — Research foundation (generative stages)

Calibration note as in §08.2: only verified sources are cited; consensus claims are phrased as consensus; numbers not pinned to a verified source are marked as engineering defaults.

### 23.1 Spec-driven development is the 2025-26 mainstream, and its failure mode is known

[GitHub Spec Kit](https://github.com/github/spec-kit) (constitution → specify → plan → tasks → implement), AWS Kiro's EARS-notation requirements, BMAD, and OpenSpec independently converged on the same shape: an explicit machine-readable specification that downstream steps verify against. The known failure mode, visible across community retrospectives, is **spec-as-bureaucracy**: documents written to be written, never verified against. Two design consequences: (a) every spec element must be *consumed* by a named downstream check (EARS AC → test skeleton → Gate 2 thresholds; module invariant → Code Review check), and the coverage matrix proves consumption; (b) the spec is **spec-anchored, not spec-as-source** — code remains the artifact; the spec is the contract it is checked against, and drift is resolved through SCRs, not silent edits.

**Design consequence:** `coverage_matrix` is a deterministic gate (Part 28); an AC with no consuming test skeleton fails Gate U3. SCR is the only legal drift channel (ADR-U02).

### 23.2 EARS makes acceptance criteria machine-checkable at the grammar level

EARS (Easy Approach to Requirements Syntax; Mavin et al., originally at Rolls-Royce, adopted by AWS Kiro) constrains requirements to five patterns (ubiquitous / event-driven `WHEN` / state-driven `WHILE` / unwanted-behavior `IF..THEN` / optional `WHERE`). The value for an agent pipeline is not elegance — it is that **conformance is lintable**: a deterministic parser can reject "the system should be fast" before any LLM spends a token on it, and a test generator can template a test skeleton from `WHEN <trigger> THE SYSTEM SHALL <response>` mechanically.

**Design consequence:** `ears_lint` (§13.31.2) is a pure-Python grammar check that runs before any Spec voter; the Ambiguity voter handles what the grammar cannot (semantically vague but grammatical statements).

### 23.3 Generation quality is bounded by context assembly, not writer prompts

The harness-engineering consensus (§08.2.2.8) applies with more force upstream: a SpecWriter given the wrong module specs produces a confidently wrong spec. Anthropic's multi-agent engineering writeup documents that context packaging and tool access dominate outcomes, and that write-heavy work parallelizes poorly — both are reflected in the ContextAssembler being a deterministic node with an explicit token budget and a `sources_read` receipt (the writer must acknowledge every manifest entry or return BLOCKED_MISSING_CONTEXT).

### 23.4 Multi-turn revision is where drafts die

[arXiv:2505.06120](https://arxiv.org/abs/2505.06120)'s ~39% multi-turn degradation motivates the **fresh-context revision protocol** (§13.25.4): a writer revising its artifact receives the current artifact + the Leader's structured fix list, never the accumulated conversation. Each revision is turn one. The per-cycle cost of re-reading the artifact is bought back in reliability.

### 23.5 Reward hacking by the implementer is the documented default, not a tail risk

The safety-removal mechanism (§08.2.2.1 — "LLMs optimize for acceptance") has a coding-stage twin: **make the test pass by weakening the test**. Community and vendor reports of agents editing assertions, deleting failing tests, or special-casing test inputs are widespread enough to treat as the default failure mode of any implement-until-green loop. Three structural defenses (§13.29.5): test files are write-locked to the implementer outside test-authoring tasks (hook, not prompt); an AST-level assertion-delta check flags removed/weakened assertions deterministically; diff-scope enforcement rejects out-of-scope file touches at the build gate.

### 23.6 Estimates need calibration, not opinions

No LLM introspection produces reliable task estimates; the practitioner consensus is reference-class forecasting from historical actuals. The `estimate_calibrator` (§13.31.3) is a deterministic lookup of median actuals per task class from the per-agent logs, with the Estimate voter limited to flagging *departures* from the reference class rather than inventing numbers. Where no history exists (first weeks), estimates are labeled `uncalibrated` and Gate U2 requires wider human scrutiny — this is the same honesty discipline as Day-0 calibration.

### 23.7 Research inputs are an injection surface

Discovery's `precedent_search` ingests arbitrary web content. Prompt-injection resistance therefore hardens beyond §09.4.2.2: the research server holds **no credentials**, its outputs are wrapped in `<untrusted_research>` tags, no agent that has consumed research output in the current run may call any L1+ tool in the same run (session isolation, enforced by the harness, §13.31.5), and the Verify pass re-derives claims from the artifact alone — an injected "finding" that isn't reproducible from the brief text dies at verification.

### 23.8 The design document is a first-class artifact, and the ecosystem splits on where it goes

Kiro's canonical flow is requirements → **design** → tasks; Spec Kit's is specify → **plan (technical)** → tasks; both agree an explicit design/technical-plan artifact belongs between intent and implementation, and disagree on whether task decomposition precedes or follows it. The consolidated methodology reference likewise carries an architecture document (system layers, data flow, module interactions, async surfaces, bottlenecks, stable interfaces) as a required Phase-2/3 output. This edition resolves the ordering with **two-pass planning** (ADR-U07, §13.36): Planning locks scope/budget/lanes at workstream granularity; the Spec stage authors the authoritative `design.md` alongside the EARS bundle; the task DAG is deterministically re-checked at Gate U3 against the finished AC↔task mapping. Design gets a real artifact and a real human acknowledgment without adding a fifth generative stage.

### 23.9 Where research is indeterminate (upstream)

- **Optimal voter counts per upstream stage.** No literature. Defaults: Discovery 4, Plan 5, Spec 5 — chosen to cover the named defect classes, revisable on action-rate data.
- **Preflight review before PR.** A single cheap heterogeneous voter before opening the PR could save Stage-5 budget on junk PRs, or could be redundant with fast-mode review. Shipped as optional, off by default; A/B during U7 (§14).
- **Reverse-interrogation question count.** The methodology reference's boundary-question procedure (archive external reference) is adopted inside the Spec Completeness voter with a default of 10 questions; the number is a knob, not a finding.

## Part 24 — Architecture integration

### 24.1 The uniform template, generative variant

Downstream (§08.1.8): `analyze → tools → vote → verify → leader → gate`. Upstream inserts generation and keeps everything else:

```
assemble (deterministic context manifest)
  → generate (SINGLE writer, fresh context, worktree for artifacts)
  → tools (deterministic checks: ears_lint, dag_check, coverage_matrix, ... — fail here is auto-REQUEST_CHANGES, no LLM spend)
  → critique-vote (parallel, independent, heterogeneous, read-only)
  → verify (per-finding fresh agent: reproducible from the artifact alone?)
  → leader (dedupe, filter <80, calibrate, verdict + STAR-L)
  → gate (U1-U4; HITL on ESCALATE_*)
  → [REQUEST_CHANGES] → revise (fresh context: artifact + fix list) → tools → ...   (max 3 cycles)
```

Coding replaces `critique-vote/verify/leader` with the deterministic build loop and defers judgment to §09 Code Review (§22.4, ADR-U01).

### 24.2 Dispatcher extension

The §09.5.5 top-level dispatcher gains four stage values. One graph, eight subgraphs, one checkpointer (ADR-005 unchanged):

```python
# autoproduct/orchestrator/dispatcher_routes.py (extended)
STAGE_SUBGRAPHS = {
    "discovery":  discovery_graph,    # §13.26
    "planning":   planning_graph,     # §13.27
    "spec":       spec_graph,         # §13.28
    "coding":     coding_graph,       # §13.29
    "code_review": review_graph,      # §09.5
    "test":        review_graph,      # test nodes live inside review_graph per §09.5.4.9-10
    "deploy_review": deploy_graph,    # §09.11
    "maintenance":   maintenance_graph,  # §09.12
}
```

Stage transitions upstream are gate-mediated exactly as downstream; the coding subgraph additionally loops over tasks internally (§13.30.2) and emits one PR per task into `code_review`.

### 24.3 Mode taxonomy, upstream

The §08.3.5 fast/standard/deep router extends with upstream classifiers (deterministic, conservative-by-default):

| Mode | Upstream meaning | Trigger |
|---|---|---|
| `fast` | Skip Discovery; thin plan (single task); spec-lite (EARS ACs only, no new contracts) | One-file change, no contract/migration/auth surface, no new dependency |
| `standard` | Full Plan + Spec; Discovery optional (existing brief referenced) | Default |
| `deep` | Full Discovery with research; Spec with full reverse-interrogation; Plan with risk-sequencing review | Greenfield feature, multi-module blast radius, any contract break, anything touching auth/billing/migrations |

Conservative default mirrors §08.3.5.1: contract, migration, auth, or new-dependency surface forces at least `standard` regardless of size.

### 24.4 What changes in 08–11 (change-control record)

Following the §11 Part 20 pattern, the deltas this edition applies to the canonical downstream docs — recorded here rather than edited in place:

1. **§08.1.8 scope table** — now eight stages (README of this edition is authoritative for the table).
2. **§08.2.2.10 errata (slopsquatting).** The "~20% of AI-generated code samples reference packages that do not exist" figure is the *all-model average* of the underlying study ([USENIX Sec '25, arXiv:2406.10279](https://arxiv.org/abs/2406.10279): 576k samples, ~19.7% average) — **commercial models measured ~5.2%, open-source ~21.7%**, and 58% of hallucinated names recurred across runs. The deterministic `slopsquat_check` design is unaffected (one predictable name is a sufficient attack surface); the prose should not imply a flat 20% for frontier commercial models.
3. **§09.5.5 dispatcher** — four new stage routes (§24.2 above).
4. **§09.7.1 tool registry** — three new MCP servers (`research`, `analytics`, `authoring`) and two new tool groups on existing servers (`planning`, `spec` toolsets); risk levels unchanged, nothing above L1 added (§13.31).
5. **§09.8.4 compounding loop** — STAR-L Landing values may now target upstream skills/templates; scope remains constraint-files-only, human-reviewed.
6. **§09.12 maintenance** — gains the hypothesis-ledger reconciliation job (§13.34.3).
7. **§11 Part 16 spec layers** — a fourth spec layer is recognized: *artifact schemas* (brief/plan/spec-bundle/SCR), validated by the harness like voter specs.
8. **§09.4 Architecture voter** — gains `spec/design.md` as its statement of intended shape: architecture findings should cite the design's "Interfaces & stability" and "Component responsibilities" sections where applicable (§13.28.2).
9. **§09.11 Deployment Review** — release notes become a roll-up of per-task changelog fragments (§13.34.4); manual-UAT-tagged ACs (`uat: true`) surface as a human acceptance checklist at Gate U3 and again pre-release.
10. **README, day-0** — superseded in place by this edition's versions (prior versions to `archive/`).
